The Tree

A field guide to its anatomy — root, siblings, ancestors, depth, height, degree & subtree.

A tree is a non-linear, hierarchical data structure: a set of nodes joined by edges in which exactly one node — the root — has no parent, and every other node has exactly one. That single-parent rule is what forbids cycles and gives the tree its character: follow any parent link upward and you must, sooner or later, arrive at the root.

Because the shape is recursive — every node roots a subtree of its own — the vocabulary matters. The eleven terms below describe where a node sits and how much hangs from it. Every example refers to the same specimen, so watch one shape accumulate meaning, term by term.

The specimen is interactive — click any node, at any point, to read its full record. Values update live.

§The specimen interactive — click any node to read its record
§The anatomy — eleven terms each entry can be demonstrated on the specimen above
01

Root radix

The single node from which the whole structure grows. It has no parent, and every other node in the tree is reached by descending from it — which also means every other node is one of its descendants. Remove the root and you no longer have a tree: you have a small forest of its subtrees.

parent(root) = none  ·  depth(root) = 0
02

Siblings germani

Nodes that share the same parent. B and C are siblings (both children of A); so are D and E, G and H, I and J — but F is an only child. One caution worth writing down: siblings are defined by parentage, not by level. D and F both sit on level 2, yet they answer to different parents (B and C), so they are not siblings.

siblings(D) = {E}  ·  siblings(F) = ∅
03

Internal nodes nodi interni

Nodes with at least one child — the branch wood of the structure, sometimes called non-terminal or branch nodes. On this specimen: A, B, C, D, E. Note that internal does not mean “two children”: C is internal with exactly one.

internal = {A, B, C, D, E} — 5 nodes  ·  degree ≥ 1
04

External nodes folia

Nodes with no children — degree 0 — also called leaves or terminal nodes, because every path through the tree ends at one of them. Here: F, G, H, I, J. A pleasing identity holds for any binary tree: the number of leaves equals the number of two-child nodes plus one — on this specimen, 5 = 4 + 1.

leaf ⇔ degree 0  ·  leaves = {F, G, H, I, J}
05

Ancestors majores

All the nodes on the path from the root down to a given node — excluding the node itself. The ancestors of H are D (its parent), then B, then A: every ancestor list climbs strictly upward and ends at the root, which itself has none. “Ancestor” and “descendant” are converse relations — B is an ancestor of H precisely because H is a descendant of B.

ancestors(H) = D ← B ← A
06

Descendants posteri

Everything inside the subtree rooted at a node, the node itself excluded: its children, its children’s children, and so on down to the leaves. The descendants of B are D, E, G, H, I, J — six nodes. A leaf, having nothing beneath it, has no descendants.

descendants(B) = {D, E, G, H, I, J} — 6
07

Depth of a node profunditas

The number of edges on the path from the root down to the node. The root sits at depth 0, and each step down a branch adds one — so depth measures how far a node is buried. Nodes of equal depth form a level; H, three edges below A, lives on level 3 together with G, I and J. (Counting conventions differ — see the footnote.)

depth(H) = 3  (A → B → D → H)
08

Height altitudo

The height of a node is the number of edges on the longest downward path from it to a leaf — a leaf is height 0, D is 1, B is 2. The height of the tree is the height of its root, which is also the maximum depth of any node: 3 here, along A → B → D → G. Depth is measured upward from the root, height downward from the node — the same path counted from opposite ends.

height(tree) = height(root) = max depth = 3
09

Degree of a node gradus

The number of children a node has — nothing subtler than that. deg(A) = 2, deg(C) = 1, deg(F) = 0. A node of degree 0 is precisely a leaf, so “external node” simply restates “degree 0” in other words.

deg(A) = 2  ·  deg(C) = 1  ·  deg(F) = 0
10

Degree of a tree gradus maximus

The maximum degree over all nodes in the tree — the width of its widest family. Here the maximum is 2, shared by A, B and E, so this specimen is a binary tree; a maximum of 3 would make it ternary, and so on. The degree of a tree bounds how many children a node may have, not how many it must.

degree(tree) = max over v of deg(v) = 2 → binary tree
11

Subtree arbor partialis

Any node of the tree together with all of its descendants and the edges between them. Every node can be regarded as the root of the subtree it defines — which is why trees are the canonical recursive structure: a tree is a root plus a collection of subtrees. The subtree rooted at D is {D, G, H} — a perfectly good tree of its own.

subtree(D) = {D, G, H}  ·  3 nodes · 2 edges

The Binary Search Tree

One law — order — and the four ways to read what grows from it.

Sheet № 1 catalogued the tree’s anatomy — root, leaves, depth, degree — without asking what the tree was for. This sheet adds the one law that turns a shape into a tool: order. In a binary search tree, every node keeps its left subtree strictly smaller and its right subtree strictly larger, and out of that single rule fall search, insertion, and deletion — each of them a walk down one path.

But a structure you can only store in is a warehouse. The second half of this sheet is about reading: traversal, the business of visiting every node exactly once. A list has one reading order; a tree must choose among them, and the useful choices number four.

The specimen is live — click its nodes, search, graft, and prune from the bench — and the reading bench in Part II plays every traversal step by step, stamping visit numbers on the nodes as it goes.

I

The ordered specimen

One new law — order. Six entries on what the law buys: search that discards a subtree per comparison, extrema at the tips, grafting and pruning that keep the law intact — and what happens when the shape goes bad.

§The specimen interactive — click nodes, or work from the bench
§The law & its consequences entries 01–06 · each demonstrable on the specimen
01

The BST propertylex ordinis

A binary tree obeys the search-tree property when, for every node, every key in its left subtree is smaller than it and every key in its right subtree is larger. Not just the immediate children — the entire subtrees, recursively. The consequence is almost geometric: each node inherits an open interval of legal keys from its ancestors (the root rules (−∞, +∞)), and every descent narrows it. Press demonstrate and every node prints its interval — the law, drawn.

∀ node · left subtree < node < right subtree — whole subtrees, recursively
specimen check:
02

Searchquaestio

To find a key k, compare it with the root: smaller — descend left; larger — descend right; equal — done. Each comparison discards an entire subtree, which is where the speed comes from. If k is present the walk ends at its node; if absent, it ends at an empty pointer — and the cost is the same either way: one root-to-node path, never more than h + 1 comparisons. Try find 45 and find 65 on the bench and watch both destinies unfold.

cost = one root-to-node path ≤ h + 1 = comparisons (h = )
balanced → O(log n) · skewed → O(n)
03

Minimum & maximumextrema

The minimum key lives at the leftmost node — follow left pointers until there are none; the maximum at the rightmost. Two walks, each no longer than the height. Note what this really is: the first and last keys of the sorted order, reachable without sorting anything. The tree keeps its extremes stored at its two outermost tips.

min = leftmost node · max = rightmost node · each ≤ h+1 steps

04

Insertioninsitio — a graft

To insert k, search for it as though it were present. The search will fail — at exactly the empty pointer where k belongs — and that dead end is the grafting point: attach a new leaf there. Because the search path respected the ordering law, the new node automatically satisfies its inherited interval. No rearrangement, no re-checking: insertion is a failed search plus one graft. Try graft 55 from the bench, or type any key 0–99.

every insertion lands as a leaf — the property is preserved by construction
05

Deletionputatio — a pruning

Pruning is where BSTs earn their reputation. A leaf detaches cleanly (case 1). A node with one child is spliced out — the child is promoted into the vacancy, subtree and all (case 2). A node with two children cannot be spliced: replace its key with the inorder successor — the leftmost node of its right subtree, which is the next key in sorted order — and prune that successor instead; it has no left child, so its own removal falls back to case 1 or 2. Click any node on the specimen and prune it from its record.

case 3: key ← inorder successor (leftmost of the right subtree), then prune the successor
06

Height & balanceaequilibrium

Every operation above walks a single path, so the height is the price of everything. The same six keys can sit at height 2 or height 5 depending on insertion order — feed a BST sorted keys and it degenerates into a chain, a linked list wearing a costume, and search collapses from O(log n) to O(n). Self-balancing trees (AVL, red-black) rotate on insertion to keep the height near ⌊log₂ n⌋ — the subject of a future sheet. For now, the field advice: never insert sorted data into an honest BST.

search O(h) → O(log n) if balanced · O(n) if skewed

07

Traversallectio — a reading

To traverse a tree is to visit every node exactly once. A list is read in one direction because it has no other; a tree must choose. The three depth-first readings differ only in when the root is read relative to its two subtrees — first, between, or last — and the root’s seat names the reading: pre-, in-, post-order. They share one recursive spine and merely swap three lines. The fourth reading, level-order, abandons recursion for a queue and reads breadth-first. Watch the mechanism strip on the bench: depth-first readings drive a call stack; level-order drives a queue.

N = the node · L = left subtree · R = right subtree — the root’s seat names the reading
read(node): if node = ∅: return ← every reading shares this spine <left> <node> <right> ← only the seating changes
08

Preorderradix prius

Read the node, then its left subtree, then its right. Two facts make preorder useful. First: the first key emitted is always the root. Second: feed the whole sequence into an empty BST and the identical tree regrows — preorder is a build order, which is why it’s the standard choice for copying and serializing trees. It also reads expressions in prefix (Polish) notation.

preorder(node): if node = ∅: return visit(node) ← the root first preorder(node.left) preorder(node.right)
first emitted = the root · rebuild: insert in this order
live:
09

Inorderradix media

Left subtree, node, right subtree. On an arbitrary binary tree, inorder is just one more ordering. On a BST it is the sorted order: the recursion reads the smaller keys first, the node between, the larger after — ascending, every time, with no sorting performed. That is the tree’s secret: it isn’t so much searched quickly as it is sorted structurally, and inorder is the reading that lets you see it. It is also the cheapest BST validator there is — run it, and check that the output ascends.

inorder(node): if node = ∅: return inorder(node.left) visit(node) ← the root in the middle inorder(node.right)
inorder(BST) = keys ascending, zero comparisons spent
live:
10

Postorderradix postrema

Both subtrees first, the node last — children before parent, always. That ordering is exactly what safe deletion of an entire tree requires (no node is freed while it still has children to free), and what bottom-up computation requires: subtree sizes, heights, and sums are all naturally postorder. The last key emitted is the root — preorder’s mirror. Postorder reads expressions in postfix (Reverse Polish) notation.

postorder(node): if node = ∅: return postorder(node.left) postorder(node.right) visit(node) ← the root last
last emitted = the root · subtree aggregates compute bottom-up
live:
11

Level-orderper gradus

Read level 0 left to right, then level 1, and so on — the tree unrolled row by row. No recursion: a queue does the work. Dequeue a node, visit it, enqueue its children; FIFO order becomes breadth order. Level-order answers the questions the depth-first readings cannot see: how wide the tree is, what each row sums to, which nodes sit nearest the root.

levelorder(root): queue ← [root] while queue not empty: node ← queue.dequeue() ← FIFO becomes breadth visit(node) if node.left: queue.enqueue(node.left) if node.right: queue.enqueue(node.right)
a queue, not recursion: dequeue → visit → enqueue children

1 · Homogeneous in Data Structures

Homogeneous = all elements are of the SAME data type

A homogeneous data structure contains elements of the same data type. An array is the classic example — every slot must hold an int (or whatever type it was declared with).
int numbers[5] = {10, 20, 30, 40, 50};  // all int → homogeneous ✔

Homogeneous vs Heterogeneous

HomogeneousHeterogeneous
All elements same typeElements can be different types
int arr[] = {1,2,3};struct Student { char name[20]; int age; float gpa; };
Example: arraysExample: structs, class objects, Python lists
struct Student {
    char name[50];   // string
    int age;         // integer
    float gpa;       // float
};                   // mixed types → heterogeneous ✔

Why homogeneity matters

  • Memory efficiency & O(1) access — equal-sized elements let the computer compute any address instantly.
  • Type safety — the compiler knows every element's type; errors are caught early.
  • Predictable operations — sorting/searching behave consistently.

🧮 Live demo: O(1) address calculation

Array addressing formula: address = base + (index × size) — this only works because all elements are the same size!

💡 Note: Python lists are actually heterogeneous (mixed types allowed), but NumPy arrays are homogeneous — that's why NumPy is much faster for numerical work.

3 · Post-order — Deeper Dive

Left → Right → Root · a node prints only when BOTH subtrees are finished

Bigger tree, full trace

Post-order: 8 9 4 5 2 6 7 3 1
🧠 Mental model: a node's value prints on its third visit — passed going down-left, passed returning from the left, and finally when arriving back from the right.

Iterative post-order — Method A: Two Stacks

Trick: run modified pre-order (Root → Right → Left) and reverse the result → post-order!

void postorderTwoStacks(struct Node* root) {
    struct Node *s1[100], *s2[100];
    int top1 = -1, top2 = -1;
    if (root == NULL) return;
    s1[++top1] = root;
    while (top1 != -1) {
        struct Node* node = s1[top1--];      // pop s1
        s2[++top2] = node;                   // push s2
        if (node->left)  s1[++top1] = node->left;
        if (node->right) s1[++top1] = node->right;
    }
    while (top2 != -1)                       // drain s2 = reversed
        printf("%d ", s2[top2--]->data);
}

Method B: One Stack with lastVisited (interview classic)

void postorderOneStack(struct Node* root) {
    struct Node* stack[100]; int top = -1;
    struct Node *current = root, *lastVisited = NULL;
    while (current != NULL || top != -1) {
        while (current != NULL) {            // go as far left as possible
            stack[++top] = current;
            current = current->left;
        }
        struct Node* peek = stack[top];
        if (peek->right != NULL && lastVisited != peek->right) {
            current = peek->right;           // right subtree not done yet
        } else {
            printf("%d ", peek->data);       // safe to print now
            lastVisited = stack[top--];      // pop
        }
    }
}
🔑 The whole trick is one condition: lastVisited != peek->right — it answers "did I come from the left (go right first) or the right (now print)?"

Where post-order is actually REQUIRED

Any problem where a parent's answer depends on its children's answers:

int height(struct Node* root) {          // height = children first
    if (root == NULL) return 0;
    int leftH  = height(root->left);     // 1. left
    int rightH = height(root->right);    // 2. right
    return 1 + (leftH > rightH ? leftH : rightH);  // 3. root LAST
}

void freeTree(struct Node* root) {       // deletion: children first!
    if (root == NULL) return;
    freeTree(root->left);
    freeTree(root->right);
    free(root);                          // can't free parent before kids
}
Expression tree:        +            Post-order → A B * C D - +
                      /   \          = postfix of (A*B) + (C-D)
                     *     -        ← how compilers evaluate
                    / \   / \          expressions!
                   A   B C   D
🎯 Rule of thumb: if a node's computation depends on its children's results, the algorithm is post-order.

4 · Prefix, Infix & Postfix Notation

Three ways to write the same expression — computers prefer the unambiguous ones

NotationOperator positionExampleAlso called
InfixBetween operandsA + BNormal human notation
PrefixBefore operands+ A BPolish notation
PostfixAfter operandsA B +Reverse Polish (RPN)
❓ Why do these exist? Infix needs precedence + parentheses: 5 + 3 * 2 — is it 16 or 11? Prefix/postfix have zero ambiguity — no parentheses, no precedence — and evaluate in one stack pass, O(n). Compilers convert your infix code to postfix.
Infix:    (A + B) * (C - D)
Prefix:   * + A B - C D
Postfix:  A B + C D - *

Evaluating Postfix (scan LEFT → RIGHT, one stack)

  • Operand → push
  • Operator → pop two, apply, push result
⚠️ #1 mistake: the first pop is the RIGHT operand (second pop = left). Critical for - and /!
Trace: 5 3 + 8 2 - * = (5+3) × (8−2)
SymbolActionStack
5, 3push[5, 3]
+pop 3, pop 5 → 5+3 = 8[8]
8, 2push[8, 8, 2]
−pop 2, pop 8 → 8−2 = 6[8, 6]
*pop 6, pop 8 → 8×6 = 48[48] → answer 48
int evaluatePostfix(char exp[]) {
    int stack[100], top = -1;
    for (int i = 0; exp[i] != '\0'; i++) {
        char c = exp[i];
        if (c >= '0' && c <= '9')
            stack[++top] = c - '0';          // operand → push
        else {
            int b = stack[top--];            // RIGHT operand first!
            int a = stack[top--];            // left operand
            switch (c) {
                case '+': stack[++top] = a + b; break;
                case '-': stack[++top] = a - b; break;
                case '*': stack[++top] = a * b; break;
                case '/': stack[++top] = a / b; break;
            }
        }
    }
    return stack[top];
}

Evaluating Prefix (scan RIGHT → LEFT)

6 · Strict vs Full vs Complete Binary Tree

Terminology varies by textbook — know both conventions!

TermRule
Strictly binaryEvery node has 0 or 2 children — never exactly 1
Full binarySame as strict in most books (some books: all levels completely filled)
Complete binaryAll levels filled except possibly the last, which fills left → right
Perfect binaryAll levels completely filled — the perfect triangle

1️⃣ Strictly binary — 0 or 2 children only

✔ STRICT                     ✘ NOT STRICT (B has exactly ONE child)
      A                            A
     / \                          / \
    B   C                        B   C
   / \                          /
  D   E                        D

Properties: leaves L, internal I  →  L = I + 1
Total nodes n = 2L − 1  →  strict trees always have an ODD node count!

2️⃣ Full binary — ⚠️ two textbook conventions

ConventionMeaning
Standard (CLRS, GATE, GeeksforGeeks)Full = Strict (0 or 2 children), aka proper binary tree
Some university notesFull = every level completely filled (= perfect)
👉 Check your syllabus! If your exam treats strict/full/complete as three DIFFERENT trees, "full" means the completely-filled (perfect) tree.

3️⃣ Complete binary — last level fills left → right, NO gaps

✔ COMPLETE                    ✘ NOT COMPLETE
        A                            A
       / \                          / \
      B   C                        B   C
     / \  /                       / \   \
    D   E F                      D   E   F
                                     ↑ GAP! F exists but its
                                       left sibling is missing
📦 Why complete trees matter: no gaps → they pack perfectly into an array (level by level). This is exactly why heaps are complete binary trees.
Tree:      A          Array:  [A, B, C, D, E, F]
          / \          index:   0  1  2  3  4  5
         B   C
        / \  /        node at i →  left child  = 2i + 1
        D  E F                     right child = 2i + 2
                                   parent      = (i − 1) / 2

📏 Height of a complete tree = ⌊log₂ n⌋ → that's why heap operations are O(log n).

4️⃣ Perfect binary — everything filled

        A          ← level 1: 1 node
       / \
      B   C        ← level 2: 2 nodes
     / \ / \
    D  E F  G      ← level 3: 4 nodes (all leaves)

Nodes = 2^(h+1) − 1   ·   Leaves = 2^h

Master comparison

FeatureStrictCompletePerfect

Leaves same level?nonoyes

How they overlap

  • Perfect ⊂ Strict and Perfect ⊂ Complete (perfect is both at once)
  • Strict + Complete but NOT perfect: 
          A        Strict ✔ (all 0/2 children)
     / \       Complete ✔ (level 3 fills left→right)
    B   C      Perfect ✘ (C is a leaf at level 2)
   / \
  D   E

5-second exam checklist

  1. Any node with exactly 1 child? → Not strict ❌
  2. Level-order scan has a gap (right child without left sibling)? → Not complete ❌
  3. All leaves at the bottom level and everything above full? → Perfect ✅

Quick practice

Tree 1 — A(B(D,E), C(F,G)) — all three levels full Strict ✅ Complete ✅ Perfect ✅
Tree 2 — A(B(D(F,G),E), C) Strict only. D's children hang at level 4 while C has none → level 3 not filled → not complete, not perfect.
Tree 3 — A(B(D,E), C(F)) Complete only. C has one child → not strict; leaves at different levels → not perfect. Last level = D, E, F fills left→right → complete ✔

🌳 Deleting a Node from a Binary Search Tree

The Two Replacement Methods — In-order Successor & In-order Predecessor

📖 First: The 3 Cases of Deletion

Difficulty depends on how many children the node has:

🍃

Case 1: Leaf

No children → just remove it. Easy!

🪜

Case 2: One Child

Replace the node with its only child.

🌿

Case 3: Two Children ⭐

Can't just remove it — we replace its value using one of the two methods below!

⚖️ The Two Methods

Both keep the tree a valid BST — the in-order (sorted) sequence never changes.

🟢 Method 1 — In-order Successor

smallest node in the RIGHT subtree
  1. Go to the right subtree of the target
  2. Keep going LEFT until there is no left child
  3. Copy that value into the target, then delete it
🧭 How to find: One step RIGHT ➜ then all the way LEFT
DELETE 50 (successor = 60)

BEFORE                 AFTER
      50 ←delete            60 ←copied
     /  \                 /  \
   30    70             30    70
  /  \   / \           /  \     \
20   40 60  80       20   40    80
       ↑
   smallest in
   right subtree

🔵 Method 2 — In-order Predecessor

largest node in the LEFT subtree
  1. Go to the left subtree of the target
  2. Keep going RIGHT until there is no right child
  3. Copy that value into the target, then delete it
🧭 How to find: One step LEFT ➜ then all the way RIGHT
DELETE 50 (predecessor = 40)

BEFORE                 AFTER
      50 ←delete            40 ←copied
     /  \                 /  \
   30    70             30    70
  /  \   / \           /     /  \
20  40  60  80       20     60   80
    ↑
   largest in
   left subtree
💡 Memory trick: Successor = Right ➜ Left, left, left…  |  Predecessor = Left ➜ Right, right, right…
Why does the replacement always have ≤ 1 child? Because we walked all the way in one direction — there's nothing left on that side!

⚖️ Balance Factor & AVL Trees

The Self-Balancing BST — watch every rotation happen live!

🌲 What is an AVL Tree?

Invented by Adelson-Velsky & Landis (1962) — the first self-balancing BST in history.

BST property ✔Balance rule ✔Height = O(log n) guaranteed ✔

A normal BST can degenerate into a linked list (e.g. inserting 1,2,3,…,10) making search O(n). An AVL tree detects imbalance and repairs itself with rotations, so search stays O(log n) — always.

⚖️ Balance Factor (BF) — The Heart of AVL

BF(node) = Height(Left subtree) − Height(Right subtree)

Height of an empty subtree = −1  •  Height of a leaf = 0

BF valueMeaningStatus
0Both subtrees equal height✅ Perfect
+1Left is 1 level taller✅ Allowed
−1Right is 1 level taller✅ Allowed
≥ +2Left-heavy❌ Rotate!
≤ −2Right-heavy❌ Rotate!
⭐ The AVL rule: EVERY node must have BF ∈ {−1, 0, +1}. A leaf's BF is always 0.

👀 Spot the Difference

✅ Valid AVL Tree

All BF ∈ {−1, 0, +1} → balanced ✔

❌ NOT an AVL Tree

It's a valid BST, but BF = −2 breaks the AVL rule → rotation needed!

The case name = the shape of the problem path. Red node = unbalanced (|BF| = 2).

🌳 Red-Black Trees

The Self-Balancing BST Behind std::map, TreeMap & the Linux Kernel — watch it recolor & rotate live!

🌲 What is a Red-Black Tree?

Invented by Rudolf Bayer (1972), refined by Guibas & Sedgewick (1978). A BST where every node carries a color bit used to stay approximately balanced.

BST property ✔5 color rules ✔Height ≤ 2·log₂(n+1) ✔
✅ C++ std::map / set✅ Java TreeMap / TreeSet✅ Linux kernel (CFS scheduler)

Less strictly balanced than AVL, but far fewer rotations on updates → the industry favorite for frequent insert/delete workloads.

📏 The 5 Golden Rules

Every Red-Black tree must satisfy ALL of them — the playground checks them for you!

#RuleMeaning
1️⃣Color ruleEvery node is RED or BLACK
2️⃣Root ruleThe root is always BLACK
3️⃣NIL ruleEvery empty leaf (NIL) counts as BLACK
4️⃣No Red-Red ⭐A RED node can never have a RED child
5️⃣Black-Height ⭐Every root→NIL path contains the same number of BLACK nodes
💡 Why it works: Rule 5 makes all paths equal in blacks, Rule 4 caps reds at 1-per-black → longest path ≤ 2 × shortest path → height ≤ 2·log₂(n+1) → all operations O(log n), guaranteed.
🎵 Mnemonic: "Roots are black, reds don't stack, blacks are counted on every track."

👀 Spot the Difference

✅ Valid Red-Black Tree

Root black • no red-red • every root→NIL path has exactly 3 blacks ✔

❌ Invalid (Rule 4 broken)

20RED → 30RED: a red-red pair! Also unequal black counts.

➕ Insertion — Always Insert RED! 🟥

A red node can only break Rule 4 locally (easy fix). A black node would break Rule 5 on every path — much worse!

🟡 Case A — Uncle is RED → RECOLOR

No rotation needed!

  2. Grandparent → RED
  3. Continue checking from the grandparent (redness moves up)
  4. If grandparent is root → recolor root BLACK (Rule 2) and stop

Same LL / RR / LR / RL shapes as AVL!

Before: RR shape, uncle black

  2. LR / RL → two rotations (straighten the zig-zag first)
  3. Recolor: middle node → BLACK, its two children → RED
  4. ✅ After a rotation fix, the violation is gone for good (no cascade!)
💡 Memory trick: Red uncle → paint it. Black uncle → rotate it.
Recoloring may cascade upward; a rotation always terminates the fix.

➖ Deletion (The Short Version)

  1. Standard BST delete — two children? Replace with in-order successor (which adopts the deleted node's color).
  2. If the removed node was RED → black-heights unchanged → no fix-up needed ✅
  3. If it was BLACK → one path lost a black node → the missing black is treated as a "double-black".
  4. Double-black is fixed by examining the sibling: recolor / rotate cases (1–4), pushing or transferring blackness until Rule 5 is restored.
