1.1 Where analysis and design fit: the SDLC

Before understanding Object-Oriented Analysis and Design, you need to understand where analysis and design fit into software development. A typical software development process moves through six phases, and modern development is often iterative — analysis, design, development and testing may happen repeatedly rather than once in a strict sequence.

1.2 What is Object Orientation?

Definition — exam version Object Orientation (OO) is a way of viewing a system as a set of interacting and interrelated objects, with each object encapsulating its data and behavior.

Instead of asking only "What functions should the program perform?", OO also asks: "What objects exist in this system, what do they know, what can they do, and how do they interact?" In an object-oriented system, software is organized around objects: objects contain data, objects provide behavior, and objects interact with other objects. Objects may represent real-world entities, concepts, or software responsibilities — for example, in a Library Management System we may identify the objects Book, Member, Librarian and Loan.

Objects as self-contained components

An object is a relatively self-contained software component that (1) has its own data — e.g. a Book knows its title, author, ISBN and availability; (2) has its own functionality — e.g. checkAvailability() and reserve(); and (3) interacts with other objects — e.g. Member → borrows → Book. Because responsibilities are organized into objects, components can potentially be reused, modified, replaced and tested independently.

Modern perspective Objects are software abstractions, not literally "real-world things". For example, PaymentService may be an object even though it is not a physical object.

1.6 Objects, attributes, methods, state and behavior

An object can be thought of as a software entity that knows things (its attributes/state) and does things (its methods/behavior). The concept of objects has historical roots in languages such as Simula.

  • Attribute — a piece of data or property of an object; attributes describe the state of an object. Different objects of the same class can have different attribute values (Car 1: colour = Red, model = Toyota; Car 2: colour = Blue, model = Honda).
  • Method — what an object can do; a method implements some behavior of the object.
  • State — what the object is/knows at a particular time, represented by attributes (e.g. colour = Red, manufacturer = Toyota, cost = 8,000,000).
  • Behavior — what the object can do, represented by methods (e.g. drive(), stop(), openDoor()).

Class vs object — the house analogy

House blueprint = class. Actual house = object. The class is the plan; the object is a real instance built from that plan. From one Employee class we can create many objects — employee1 (John), employee2 (Jane), employee3 (Mark) — all belonging to the Employee class but holding different values.

Definition — instance An instance is a particular object created from a class — "a single person, thing or concept in the application domain" and another word for a single object. Each instance has its own state. Example: Peter (name = Peter, age = 15) is an instance of the Student class.

1.8 Message passing

Objects need to communicate with one another — this communication is called message passing. A message is essentially a request to an object to perform some operation, e.g. Customer → placeOrder() → OrderService. The receiving object executes the appropriate method. Analogy: a person says "Prepare the soup" — the chef receives the request and performs prepareSoup(). Message = "Prepare soup", method = prepareSoup().

How message passing works — three steps

  1. Sender — one object sends a message.
  2. Receiver — another object receives the message.
  3. Method execution — the receiver executes the corresponding method; a result may then be returned.

Components of a message

Client and server objects

In an object interaction, the message sender acts as the client and the message receiver acts as the server for that particular request. If Alex (Customer) sends placeOrder() to Lawrence (SalesPerson), then Alex is the client and Lawrence is the receiving/server object: the customer requests a service and the salesperson provides it.

1.9 Method signature

A method has a signature that identifies the operation — the combination of the method name and the parameter list. For getMyFundsFromBank(String bankName) the signature is getMyFundsFromBank(String). Exact rules for what constitutes a signature vary between programming languages, but the core idea is always name + parameters.

Abstraction

Abstraction means focusing on the important aspects of something while ignoring unnecessary details. It answers "What does this object do?" rather than "How exactly does it do it?"

  • Map example: a map is an abstraction — a road map shows roads, cities, routes and distances, while a geological map of the same area shows rock types, geological structures and boundaries. The same geographical area is represented differently depending on what information is important.
  • Smartphone call example: the user sees only [ Accept ] [ Reject ]. They do not need to know how the network identifies the phone, how signalling works, how audio packets are transmitted, or how the OS manages the call. The complexity is hidden and the user interacts with a simple interface.
Definition — abstraction Abstraction hides unnecessary complexity and exposes the essential functionality.

Encapsulation

Encapsulation means packaging the data and the operations that work on that data together inside an object/class, and controlling access to the object's internal state. Outside code should not normally manipulate internal data directly — instead, controlled operations enforce the rules.

BankAccount
- balance : double
- accountNumber : String
+ deposit()

  • Data hiding means restricting direct access to internal data or implementation details: private double balance; Instead of account.balance = -500000; (illegal direct manipulation), we provide controlled operations account.deposit(5000) and account.withdraw(1000).
  • This allows the class to enforce rules: withdraw(amount) performs the withdrawal only if amount ≤ balance, otherwise the transaction is rejected.
Advantage 1 · Data Integrity
Data can only be modified through controlled operations.
Advantage 2 · Security
Sensitive internal information can be protected.
Advantage 3 · Control
The class decides which operations are allowed.
Advantage 4 · Flexibility
Internal implementation can change without affecting users of the class.
Advantage 5 · Reduced Complexity
Users do not need to understand internal implementation.
Exam classic — Encapsulation vs Abstraction Encapsulation: "How do we package and protect the data and implementation?" (balance is protected from direct access).
Abstraction: "What should we expose and what unnecessary complexity should we hide?" (the user only needs to know deposit/withdraw/getBalance — not how the bank internally updates the balance).
Definitions to memorize: Encapsulation = separating an object's external interface from its hidden internal implementation. Abstraction = hiding unnecessary complexity and exposing essential functionality.

Inheritance

Inheritance is a relationship between classes where one class derives from another. The existing class is called the parent / base / superclass; the new class is the child / derived / subclass. Inheritance is a mechanism for sharing and reusing attributes and behaviors.

Suppose Car, Bike and Truck all need vehicleNumber, brand, speed, start(), stop(). Instead of repeating these in every class, define them once in Vehicle and let Car extends Vehicle, Bike extends Vehicle, Truck extends Vehicle.

Inheritance: children reuse common attributes and behavior from Vehicle
Caution — when to use inheritance Inheritance is useful when there is a genuine "is-a" relationship (a Car is a Vehicle). Modern OO design often prefers composition over inheritance when appropriate, because excessive inheritance can create rigid class hierarchies.

Polymorphism

Polymorphism literally means many forms (poly = many, morph = form). It allows the same operation/interface to produce different behavior depending on the object involved.

  • Parking example: every Vehicle has calculateParkingFee(), but a Car, Bike and Truck each calculate the fee differently. The caller simply invokes vehicle.calculateParkingFee() and the behavior depends on the actual vehicle type.
  • Payment example: Card, PayPal and BankTransfer each implement pay(). The application calls payment.pay() without needing to know the detailed implementation.

1.11 Cohesion

Cohesion measures how strongly the responsibilities, methods and data of a class belong together around a single meaningful purpose. It is concerned with the inside of one class/module.

Quick test for any exam scenario Ask: "Does this class have one clear purpose?" If YES → high cohesion. If NO → low cohesion — split the class into focused services.

1.12 Coupling

Coupling refers to the degree of dependency between software modules/classes — the strength of the connections between classes. If two classes depend heavily on each other → high coupling. If they are relatively independent → low coupling.

  • High coupling: a chain A → B → C → D where changing Class B requires changes in A, C and D. The system becomes difficult to maintain, test, modify, and more vulnerable to changes.
  • Low (loose) coupling: classes depend on an abstraction/interface rather than a specific implementation. If Order depends directly on MySQLDatabase, switching to MongoDB forces changes to Order (high coupling). Instead, let Order depend on a Database interface implemented by both MySQLDatabase and MongoDatabase — the Order class doesn't care which database is used.
Real-world analogy High coupling = a phone charger that works only with one specific phone model. Loose coupling = a USB-C standard charger that works with many compatible devices.

1.13 Worked example — Smart Parking System (Activity 1)

✏️ Worked example — apply all Week-1 concepts

A smart parking system manages parking spaces in a shopping mall. When a vehicle enters, the system assigns an available parking slot. When the vehicle leaves, the system calculates the parking fee based on the duration. The system supports Cars, Bikes and Trucks.

Part A — Identify at least 7 classes; B — 3 attributes each; C — 2 methods each; D — inheritance hierarchy; E — encapsulation choices; F — polymorphism; G — high cohesion class; H — reduce coupling.

Solution

A + B + C — Classes with attributes and methods:

  • ParkingSystem — attrs: mallName, totalSlots, operatingHours; methods: assignSlot(), releaseSlot()
  • ParkingSlot — attrs: slotID, slotType, isOccupied; methods: occupy(), vacate()
  • Vehicle — attrs: vehicleNumber, vehicleType, entryTime; methods: getDuration(), getVehicleType()
  • Car / Bike / Truck (subclasses of Vehicle)
  • Ticket — attrs: ticketID, issueTime, exitTime; methods: calculateDuration(), printTicket()
  • Payment — attrs: amount, paymentMethod, timestamp; methods: processPayment(), printReceipt()
  • FeeCalculator — attrs: hourlyRateCar, hourlyRateBike, hourlyRateTruck; methods: calculateFee()
  • Driver — attrs: name, licenceNo; methods: parkVehicle(), collectVehicle()

D — Inheritance: Vehicle is the parent; Car, Bike, Truck are children (each is-a Vehicle and inherits vehicleNumber, entryTime, getDuration()).

E — Encapsulation: make ParkingSlot.isOccupied and Payment.amount private. Hiding isOccupied prevents outside code from marking a free slot as occupied without going through assignSlot() — the system keeps slot allocation consistent. Access is controlled via occupy()/vacate() and processPayment(), which can validate rules (e.g. payment only after exit time is known).

F — Polymorphism: calculateFee() (or calculateParkingFee()) should behave differently for Car, Bike and Truck — same method name, different fee logic per vehicle type; the caller just calls vehicle.calculateParkingFee().

G — Cohesion: FeeCalculator has high cohesion — every method and attribute is about computing fees; it has one clear purpose.

H — Coupling: if ParkingSystem directly constructs and calls a specific CashPaymentProcessor, replacing it with card payment requires editing ParkingSystem (unnecessary dependency). Reduce it by making ParkingSystem depend on a general Payment interface — the payment method becomes swappable.

Object-Oriented Languages

Week 2 · Object-Oriented Languages

2.1 Introduction

A number of OOP languages are available today, with some differences between their capabilities and the extent to which they follow the OO paradigm. An OO language is based on a paradigm of objects (data + behavior): objects represent real-world entities. For example, a Car object has attributes (color, model, speed) and methods (start(), stop(), accelerate()). Common OO languages include Java, C#, C++, Python, Kotlin, Swift and TypeScript. This lecture examines the key features of OO languages and their limitations.

2.2 Strong typing

Definition Strong typing is the degree of discipline that a language enforces on the programmer when declaring variables: "Every data value and object that is used must belong to an appropriate type for its context."

Most modern languages are strongly typed. For example, int x = "Hello"; produces a compile-time error in Java. Strong typing prevents type mismatch errors and reduces runtime bugs.

2.3 Static vs dynamic typing

  • Statically typed — types are checked at compile time. Examples: Java, C++, C#.
  • Dynamically typed — types are checked at run time. Examples: Python, Ruby, JavaScript.
  • Hybrid — some languages offer a hybrid approach. Examples: TypeScript, Kotlin.
TypingAdvantagesDisadvantages
StaticErrors caught at compile time; better performance; easier IDE supportLess flexible; verbose code
DynamicFlexible; faster to write; less verboseErrors occur at runtime; harder to debug; slower performance
"Verbose code" simply means… …writing more lines or more detailed code to achieve something. Statically typed Java is verbose; dynamically typed Python is less verbose.

2.4 Garbage collection

Garbage collection (GC) is the automatic process of freeing memory occupied by objects that are no longer used by the program. It is important for memory management in systems that create and delete many objects during execution — objects must be removed from memory when they are deleted, otherwise the system may run out of memory in which to execute. GC helps prevent memory leaks and out-of-memory errors in long-running programs. In Java, objects are stored in heap memory.

Types of garbage objects in Java

1 · Nullified objects
An object whose reference is explicitly set to null (e.g. student = null;) — no reference points to it anymore.
2 · Out-of-scope objects
Objects created inside a method/block become garbage when the execution leaves that scope.
3 · Unreachable via reassignment
When a reference is reassigned to a new object, the old object loses its only reference and becomes unreachable garbage.

2.5 Standardized class libraries

A standardized class library is a collection of predefined classes and interfaces provided by the language so programmers can reuse tested code instead of writing everything from scratch. Key features:

  • Cross-platform compatibility — works on any OS where the language runtime runs (e.g. anywhere Java runs).
  • Pre-tested and reliable — reduces errors and development time.
  • Object-oriented — libraries provide ready-to-use classes, objects and methods.
  • Consistent naming and usage conventions across libraries.

2.6 Dynamic loading

Dynamic loading is the ability of a program to load classes or libraries into memory at runtime, rather than at compile time. Classes are loaded only when needed, improving memory usage and flexibility.

2.7 Limitations of object orientation

OO development is powerful but is not ideally suited to every kind of application. The lecture highlights two families of applications where OO may be a poor fit:

✏️ Exercise — when is OO not the best choice?

In what scenarios might Object-Oriented development not be the best choice, and what limitations or mismatches with the nature of the problem contribute to this?

Solution

OO is a poor fit when the nature of the problem does not decompose naturally into interacting objects:

  1. Record-based, data-centric systems: when the main operations are CRUD on structured records, an RDBMS is more natural; forcing objects onto tables adds mapping overhead (ORM) with little modeling benefit.
  2. Computation-centric systems: when the core is one large, complex calculation, splitting it into objects increases the number of objects and overall complexity, and can reduce performance.

In both cases the mismatch is between the problem's structure (records or algorithms) and OO's strength (modeling interacting entities with state and behavior).

Modelling Concepts & UML

Week 3 · Modelling Concepts

3.1 Model vs diagram — the critical distinction

Exam definition pair Model = a simplified/abstract representation of a system — it represents the whole system and its important elements and relationships (the complete blueprint; WHAT we are representing).
Diagram = a particular view of a model — it shows only a specific part or aspect of the model (HOW we represent/show it).

The house analogy

Think about a house. The model is the complete idea/representation of the house — it tells us about the rooms, the relationships between rooms, doors, windows, the structure and how things are organized. Different diagrams are visual ways of showing parts of that model:

  • Floor plan → shows room arrangement
  • Electrical diagram → shows electrical connections
  • Plumbing diagram → shows water connections

In software engineering

Suppose we are developing a Library System. The model represents the system's important concepts and relationships: Student borrows Book; Librarian manages Book; Book belongs to Library. We can represent different parts of that model using diagrams:

  • Class Diagram → shows classes and their relationships
  • Use Case Diagram → shows actors and their interactions with the system
  • Sequence Diagram → shows how objects interact over time
Remember A model can be represented using several diagrams — each diagram is one view of the same underlying model.

Why are models needed?

Software systems are complex. Models help us simplify, understand, communicate and manage that complexity. Diagrams in particular serve to: communicate ideas, understand structure and relationships, test ideas, and generate new ideas.

3.2 General rules of modeling

Rule 1 · Simplicity
Keep the model as simple as the purpose allows — don't model what you don't need.
Rule 2 · Consistency
Different parts/views of the model must not contradict each other.
Rule 3 · Completeness
The model must cover everything relevant to its stated purpose.
Rule 4 · Hierarchical representation
Organize the model in levels — high level first, details at lower levels.

3.3 What is UML?

Definition — UML Unified Modeling Language — a standard language for specifying, visualizing, constructing and documenting software systems.

UML has three building blocks: Things (the model elements, e.g. classes, actors, use cases), Relationships (how things connect, e.g. associations, dependencies, generalizations) and Diagrams (the views that group things and relationships into pictures).

An ATM allows a customer to insert a card, enter a PIN, check balance, withdraw money and receive a receipt. The ATM communicates with the bank system. Which diagram shows actors and their goals? Which shows the sequence of interactions during cash withdrawal?

4.1 What is use case modeling?

Definition Use Case Modeling is a requirements engineering technique used to identify, elicit and document the functional requirements of a system. It describes how users interact with a system to achieve their goals — the system described from the user's perspective.

Use cases are primarily written descriptions, not diagrams. A Use Case Diagram in UML visually shows actors, use cases and their relationships — but the real content of a use case is its text.

4.2 Functional vs non-functional requirements

Functional Requirement (FR)Non-Functional Requirement (NFR)
DefinitionA statement of what the system should doA constraint on how the system should operate or be implemented (a quality requirement)
ATM examplesValidate ATM card · Validate PIN · Dispense cash · Display account balanceValidate PIN within 3 seconds · Communication must use encryption · Available 99.9% of the time · Respond within 2 seconds · Passwords securely stored · Built with a specific language

Exam tip Spot the pattern: "The ATM shall validate the PIN" = functional. "The ATM shall validate the PIN within 3 seconds" = non-functional. The timing/quality constraint is what makes it non-functional.

4.3 Use case vs scenario

Definitions Use case — a story describing how an actor uses a system to achieve a goal; a collection of related scenarios.
Scenario — one specific path through that use case.

Example — Withdraw Cash: the customer inserts the ATM card, enters the PIN, selects "Withdraw Cash", enters the amount, the system checks the account and dispenses cash. That whole interaction is the use case Withdraw Cash. Its scenarios include:

  • Scenario 1 — Successful withdrawal: correct PIN, withdraws Rs. 10,000.
  • Scenario 2 — Wrong PIN: the customer enters an incorrect PIN.
  • Scenario 3 — Insufficient balance: requests Rs. 50,000 but has only Rs. 20,000.
  • Scenario 4 — Daily limit exceeded: already withdrawn the maximum allowed amount.

Use Case Diagrams

Week 5 · Use Case Diagrams

5.1 What is a use case diagram?

A Use Case Diagram is a UML diagram used to show who interacts with a system, what the system can do, and how actors and system functions are related. It gives a high-level view of the functional requirements of a system.

5.2 The four main components

1 · Actor
A person, system, device or other entity that interacts with the system — a role, not a specific person (Doctor ✓, Dr. John ✗). Drawn as a stick figure for humans, or a rectangle labelled «actor» for an external system.
2 · Use case
Something an actor wants the system to do — short, meaningful, action-like names. Drawn as an oval.
3 · System boundary
A rectangle surrounding the use cases; the system name is written at the top. Shows what belongs to the system and what is outside.
4 · Relationships
Association, «include», «extend» and generalization — see below.

5.3 Association

An association shows that an actor interacts with a use case. Notation: a solid line between actor and use case — Customer ─── Place Order. A customer can be associated with several use cases: Search Product, Place Order, Cancel Order, Check Order Status.

Identifying actors and use cases

  1. Identify the actors — who or what interacts with the system?
  2. Identify what each actor wants to do — these become candidate use cases.

Example — University System, actor Student: Enroll in Course, View Results, View Timetable, Request Transcript.

5.4 «include» — the MUST relationship

«include» = MUST happen «include» is used when one use case must use the behavior of another use case — the included behavior is mandatory. The base use case cannot properly complete without the included use case.
Direction: Base (client) → Included (supplier), drawn as a dashed arrow: Check Order Status –«include»→ Login.

Example: if several functions require login — Check Order Status → Login, View Profile → Login, Change Password → Login — then Login can be separated as a reusable use case included by each of them. That reuse of common, mandatory behavior is the whole point of include.

5.5 «extend» — the EXTRA relationship

«extend» = ADD EXTRA BEHAVIOR «extend» is used when one use case adds extra behavior to another existing use case — and the base use case can still work without the extension.
Direction: Extension → Base (note: the arrow points the opposite way to include!): Issue Fine –«extend»→ Return Book.

Returning a book is possible by itself. If the book is overdue, Issue Fine adds additional behavior. The extension happens only under a particular condition.

5.6 Generalization — the IS-A relationship

Generalization represents an "is-a" relationship between use cases, creating a parent–child relationship where the child is a more specific version of the parent. Example: Search is the parent; Search by Author and Search by Call Number are children. Notation: a directed arrow with a triangular arrowhead, pointing from child to parent.

Activity Diagrams

Week 6 · Activity Diagrams

6.1 Introduction

Activity diagrams are "OO flowcharts" — they can show both data flow and control flow, and allow us to model a process as a collection of activities and transitions between those activities. They are particularly useful for process modeling, behavior visualization, requirement analysis, process improvement, and communication among stakeholders. The main purpose of an activity diagram is to model the flow of activities and actions within a system or process. They can also illustrate how actions are distributed across actors or components using swimlanes.

6.2 Elements of an activity diagram

  • Action nodes — represent executable steps.
  • Control nodes — manage the flow of execution:
    • Initial and final nodes (final nodes have two varieties: activity final and flow final)
    • Decision and merge nodes
    • Fork and join nodes
  • Object nodes — represent objects or data used within the activity.

An activity represents a behavior composed of one or more actions — a network of nodes connected by edges. Every activity begins with an initial node and ends with a final node.

6.3 Actions

Actions are the fundamental units of behavior in an activity diagram. They are represented as rounded rectangles, and the label may be written in plain English or pseudo-code. When written in English, the label should be a verb or verb phrase, since actions denote something being performed. Actions have three key properties:

Atomic
An action is not decomposed within the activity — it is treated as a single step.
Uninterruptible
Once an action begins execution, it runs to completion.
Instantaneous
An action is assumed to take negligible time relative to the overall activity.

Action flows (also called edges or paths) illustrate the transitions from one action state to another.

6.4 Starting and stopping

  • Initial node — the starting point of an activity: a solid filled circle.
  • Activity final node — termination of the entire activity: a bull's-eye symbol (filled circle inside an outer circle).
  • Flow final node — a circle containing an X. It terminates only the specific flow reaching it, without ending the entire activity.

6.5 Decision and merge nodes

Decision and merge nodes are represented by a diamond shape and control alternative flows within an activity:

NodeFlowsBehavior
Decision nodeOne incoming, multiple outgoingEach outgoing flow is guarded by a condition (guard), e.g. [is junk]. Only one path is selected at runtime.
Merge nodeMultiple incoming, one outgoingCombines alternative paths without synchronization — any one incoming flow can continue execution.

6.6 Fork and join nodes — concurrency

Activity diagrams support modeling of concurrent flows of execution — activities that can proceed in parallel. A fork node splits one flow into multiple concurrent flows; a join node synchronizes concurrent flows back into a single flow. Fork and join are analogous to decision and merge respectively — the critical difference is concurrency:

Decision / MergeFork / Join
Fork: flows outDecision has one flow in and multiple flows out — but selects a single outbound flowFork has one flow in and multiple flows out — and ALL outbound flows occur concurrently
Join: flows inMerge: any one incoming flow can continueJoin: ALL incoming flows must be completed before the outbound flow begins
Guards?Yes — outgoing flows carry guard conditionsNo — all branches simply run in parallel
Exam classic — decision vs fork Both have one incoming and multiple outgoing flows. A decision chooses ONE path (guarded alternatives); a fork starts ALL paths concurrently. Similarly, merge accepts any one incoming flow; join waits for every incoming flow to finish.

6.7 Notation reference

Activity diagram notation — initial, finals, action, decision/merge, fork/join, object node, swimlane

6.8 Swimlanes (partitions)

Elements in an activity diagram can be organized using partitions (swimlanes). A partition indicates responsibility for performing actions within the activity. Depending on the kind of modeling:

Modeling contextPartitions may represent
Business modelBusiness units — departments or divisions, business actors or roles, organizations
System modelingSystems, subsystems, external systems
Application modelingObjects, components, logical entities within the application

Lecture example — airport check-in

  • Swimlane: Passenger — showing ticket at check-in counter, checking luggage, paying fee (user/actor behaviors).
  • Swimlane: Passenger Services — verifying ticket, referring passenger to customer services, accepting luggage, issuing boarding pass (service/system responsibilities).

6.9 Object flow

Object flow refers to the creation and modification of objects by activities. An object flow arrow from:

  • action → object — the action produces, creates or updates the object;
  • object → action — the action uses, reads or requires the object.

Show only the important objects on an object flow. You can show the object's state by writing the state name in square brackets below the object's name — e.g. Order [filled].

● → Get mail → ◇ (decision) with two guarded outgoing flows: [is junk] → Bin mail → ◎ and [not junk] → Open mail → ◎. The two final nodes can be merged into one activity final via a merge node. (See the mini-flow drawn in the notation reference above.)

✏️ Exercise 3 — creating a document

Open the word processing package → create a file → save under a unique name → type the document. If graphics are necessary, open the graphics package, create graphics and paste them into the document. If a spreadsheet is necessary, open the spreadsheet package, create the spreadsheet and paste it. Save the file → print a hard copy → exit.

Solution
  1. ● → Open word processor → Create file → Save file under unique name → Type document.
  2. After typing, a decision: [graphics necessary] → Open graphics package → Create graphics → Paste into document; [not necessary] → skip to next decision.
  3. A second decision: [spreadsheet necessary] → Open spreadsheet package → Create spreadsheet → Paste into document; [not necessary] → continue.
  4. Both optional branches merge back into the main flow: Save file → Print hard copy → Exit word processor → ◎.

Key idea: optional steps are modeled with decision + merge, NOT with fork/join (only one option is taken, the two options never run concurrently).

✏️ Exercise 4 — order processing (with concurrency)

The requested order is the input to receiving the order. If the order is accepted, all required information is filled in, the invoice is sent and the payment is accepted. When the payment is accepted, the order is shipped. This business flow allows order shipment during the sending of the invoice and confirmation of payment. Finally, the order is closed.

Solution

"Shipment during sending the invoice and confirmation of payment" is the signal for concurrent flows — use fork and join:

  1. ● → Receive order (the object Order [requested] flows in).
  2. Decision [accepted] — if accepted → Fill in all required information; if rejected → end.
  3. FORK into two concurrent flows: (a) Send invoice; (b) Confirm payment → Ship order.
  4. JOIN after "Send invoice" and "Ship order" complete → Close order → ◎.
Order processing with concurrency — the fork starts "Send invoice" and "Confirm payment → Ship order" in parallel; the join waits for both before "Close order"
✏️ Exercise 5 — company client engagement (with swimlanes)

A company follows a structured process when engaging prospective clients. A sales person contacts a client to schedule an appointment. For onsite meetings, a corporate technician prepares the meeting facilities; for offsite meetings, a consultant prepares the required equipment. After preparation, the consultant meets the client. Then the sales person sends a follow-up letter. If the client provides a statement of the problem, the consultant creates and sends a proposal; otherwise the process ends.

Solution
  1. Swimlanes: Sales Person, Corporate Technician, Consultant (the client is an external participant — it does not perform modeled actions, it only triggers conditions such as "provides statement of problem").
  2. ● → Sales Person: Contact client to schedule appointment.
  3. Decision [onsite] → Corporate Technician: Prepare meeting facilities. [offsite] → Consultant: Prepare required equipment. (These are alternatives — decision + merge, not a fork, because the meeting is either onsite or offsite, never both.)
  4. Merge → Consultant: Meet with client.
  5. Sales Person: Send follow-up letter.
  6. Decision [problem statement provided] → Consultant: Create proposal → Send proposal to client → ◎. [not provided] → ◎ (process ends).

7.2 Finding classes — noun-verb analysis

There are two common approaches for identifying classes: Noun–Verb Analysis and CRC Analysis. Noun–verb analysis works well because it is based on direct analysis of the language used in the problem domain:

  • Nouns and noun phrases in the text usually indicate classes or attributes of classes.
  • Verbs and verb phrases indicate the responsibilities or operations (methods) of a class.
Watch out Hidden classes are inherent to the problem domain but not explicitly mentioned: "Students enroll in courses offered by the university" — nouns: Student, Course, University — but the system must also track Enrollment (enrollmentID, semester, grade), a hidden class!
Beware synonyms (different words, same meaning) and homonyms (same word, multiple meanings — "Order" as purchase request vs "order" as command). Both can cause incorrect classes or operations.

7.6 Relationships

Association

An association connects two classes and represents a meaningful relationship between them — a straight line between the classes. A class may even have an association with itself (a reflexive association — e.g. one Employee manages other Employees). Associations may be decorated with multiplicity to indicate how many objects participate in the relationship.

Directed association

A directed association is a simple relationship where one class is linked to another with an explicit direction — one class directly knows about or uses another. It is one-directional and drawn as a line with an arrow pointing toward the class being referenced. Example: Car → Engine — a car knows about its engine, but an engine doesn't need to know about a specific car.

Multiplicity

Multiplicity specifies how many instances of class A can be associated with one instance of class B. It is applied to the target end of an association and denotes the number of links between each instance of the source class and instances of the target class.

NotationMeaningExample
1Exactly oneEach person has exactly one passport
0..1Zero or one (optional)A person may or may not own a car
* or 0..*Zero or more (many)A library can have zero or more books
1..*One or moreA teacher teaches one or more students
m..nRange (m to n)A team comprises 6..12 players

Generalization

The generalization icon denotes a generalization/specialization relationship (the "is-a" relationship). It appears as an association with a closed (triangular) arrowhead; the arrowhead points to the superclass, and the opposite end designates the subclass.

Dependency

A dependency is a temporary or weak relationship where one class depends on another but does not own it — drawn as a dashed arrow from the client class to the supplier class. Example: a Student depends on a Library Card to access books; the Library Card does not depend on the Student — it exists independently and can be reassigned to another student if needed.

Aggregation

Aggregation is a constrained form of association — the "has-a" / part-of relationship where one class belongs to a collection. Drawn with an empty (hollow) diamond on the side of the aggregate (the whole). Example: an Instructor is part of the Faculty.

Composition

Composition is the strong form of aggregation — the components cannot exist without the aggregate. Drawn with a solid (filled) diamond on the side of the whole; the multiplicity at that end is 1, because the parts have no meaning outside the whole, which owns them — the "is entirely made of" relationship. Example: a House is composed of one or more Rooms; each Room belongs to exactly one House; if the House is destroyed, the Rooms also cease to exist.

The six class-diagram relationships — memorize line styles, arrowheads and where the diamond sits
Exam classic — aggregation vs composition Aggregation: hollow diamond; the part can exist independently of the whole (an Instructor can exist without the Faculty; a Department exists even with no employees temporarily).
Composition: solid diamond; parts cannot exist without the whole (Rooms cease to exist when the House is destroyed; multiplicity at the whole end is 1). Test phrase: if the whole is destroyed, do the parts die too?

Interaction Diagrams: Sequence & Communication

Week 8 · Interaction Diagrams (Communication + Sequence)

8.1 What are interaction diagrams?

Interaction diagrams are UML behavioral diagrams that illustrate how objects or actors interact with one another by exchanging messages to accomplish a specific task or achieve a particular goal in a system. Their purpose:

  • Represent the communication between objects in a system.
  • Show the sequence and flow of messages exchanged between objects.
  • Describe how objects collaborate to perform a particular operation or use case.
  • Help developers understand and design the dynamic behavior of a system.

8.2 Sequence vs communication — the big comparison

Focuses on HOW objects are connectedFocuses on WHEN messages occur

Links show relationships between communicating objectsLifelines extend vertically
Message numbers (1, 2, 2.1…) indicate the order of interactionsMessages ordered top to bottom
Emphasizes the organization of objects and their relationshipsEmphasizes the timing and order of interactions

8.3 Communication diagrams

A UML Communication Diagram is an interaction diagram that illustrates how objects communicate with each other through messages to perform a task or achieve a goal. Its main elements:

1 · Objects
The participants in the interaction, shown as rectangles labelled objectName:ClassName.
2 · Links
Lines connecting objects, indicating that they can communicate with each other.
3 · Messages
Labels on links representing communication — method calls, requests or responses.
4 · Sequence numbers
Indicate the order messages are sent and processed: 1, 2, 2.1, 2.2, 3…
Message numbering — user login
  • 1: login() — first message
  • 2: validateUser() — second message
  • 2.1: checkCredentials() — a nested message within message 2
  • 3: displayResult() — third message

8.4 Sequence diagrams

A sequence diagram is a UML interaction diagram that shows how actors, objects or system components exchange messages over time to complete a scenario. It arranges participants horizontally and messages vertically, making the order of requests, responses, conditions and loops easier to understand.

When to use sequence diagrams

  • Model a specific use case or scenario — step-by-step flow of messages for one use case.
  • Design or refine system architecture — visualize how UI, business logic and database interact.
  • Clarify complex processes — break complicated workflows into clear time-ordered interactions.
  • Validate logic before implementation — confirm all interactions are defined before coding.
  • Explain system behavior to stakeholders — technical and non-technical team members.
  • Design or analyze integrations and APIs — requests/responses between services (including microservices).

Objects and lifelines

A sequence diagram contains several lifeline notations arranged horizontally across the top (they should not overlap). Each lifeline represents an object or part of the system participating in the interaction, drawn as a dashed vertical line starting from the bottom center of its object box — indicating the object's existence/lifespan during the sequence of events. Special stereotyped lifelines:

Lifeline elementRepresentsExample
ActorUsed when the sequence diagram is owned by a use caseCustomer, Student
BoundaryA system boundary / software element users interact withUI screens, menus, database gateways
ControlA controlling entity or manager — organizes and schedules interactions between boundaries and entities; the mediatorWithdrawalController
EntitySystem dataCustomer entity managing customer data, BankAccount

Activation bars and messages

The activation bar is the thin box placed on the lifeline, indicating that an object is active (or instantiated) during an interaction. Its length indicates the duration the object stays active. The message caller is active when it sends the message; the message receiver becomes active when it receives the message and begins processing it.

A message arrow represents a message sent from one object to another. Messages can flow left to right, right to left, or back to the same object (self-message). A message arrow includes a message signature:

Message signature format attribute = message_name(arguments) : return_type
Message typeMeaning
SynchronousThe sender waits for the receiver to process the message and return before carrying on
AsynchronousThe caller does not wait — it can send other messages before the receiver finishes
Return messageThe receiver is done processing and returns control to the caller (drawn dashed)
Participant creation messageObjects don't have to live for the whole sequence — participants can be created by a message
Participant destructionParticipants no longer needed can be deleted — an X at the end of the lifeline
Reflexive messageAn object sends a message to itself

UML diagrams generally permit comments — a rectangle with a folded-over corner, linked to the related element with a dashed line.

8.5 How to draw a sequence diagram — 7 steps

  1. Identify the use case — define the specific scenario to model.
  2. Identify the objects and actors — e.g. Librarian, Online Library Management System, User Credentials Database, Email System.
  3. Describe the use case in detail — a comprehensive description reveals the interactions that should appear in the diagram.
  4. Identify the sequence of interactions — e.g. librarian requests account creation → selects account type → enters details → details checked against credentials database → account created → details emailed to user.
  5. Arrange actors and lifelines horizontally.
  6. Add messages and interaction details (with activation bars).
  7. Review and refine the diagram.
Best practices Draw smaller sequence diagrams · avoid unnecessary or repetitive diagrams · use clear, consistent naming · maintain logical ordering and alignment · limit the number of objects per diagram · highlight alternative or conditional flows with fragments.

FR = what the system should do ("validate PIN"). NFR = constraint on how it operates ("validate within 3 seconds", encryption, 99.9% availability, 500 concurrent users).
Use casesActor typesprimary / supporting / offstage
Primary: has the goal, uses the system (Customer). Supporting: provides a service TO the system (Payment Gateway). Offstage: has an interest, never touches the system (Tax Authority). Actor = role, not name.
Use cases«include» vs «extend»MUST vs EXTRA
Include: mandatory reuse, Base → Included (Deposit Funds → Update Balance; Place Order → Login). Extend: optional addition, Extension → Base (Calculate Bonus → Deposit Funds; Issue Fine → Return Book).

Aggregation: hollow diamond; part can exist independently (Instructor–Faculty; Department–Employee). Composition: solid diamond at the owner, multiplicity 1; parts die with the whole (House–Room; "is entirely made of").

Decision: one in, guarded flows out, ONE selected. Fork: one in, ALL flows out concurrently. Merge: any one incoming continues. Join: waits for ALL incoming to complete. Flow final kills one flow; activity final kills everything.
